# Optional-addon version boundaries (2026-10-25)

## Evidence and reproduction

- `tests/compat/version-boundaries.json`: 151 historical dependency tuples. `tools/compat_versions.py` resolves existing production profiles, replaces verified release pins, and runs ordinary dedicated servers; `--bare` removes Federation and its test JAR.
- `tests/compat/version-boundaries-evidence.json`: 170 server experiments, two development-client runs, 122 upstream JAR artifacts, resolved tuples, metadata, binary contracts, reports, console hashes and differential-control sources. The 1,287 reported GameTest outcomes include intentional negative controls and fixture failures; they are not a production pass-rate metric.
- All server comparisons use production JAR SHA256 `ddb61e07242c25bc13bf77de60b3250677224e902298db3758ba1c295ed46bf0`. Three regular fixture snapshots occur; use the recorded per-run hash and changed class entries, not an assumption of identical fixtures. Live Java source can differ from the tested JAR.
- Findings: `docs/compatibility/minimum-versions.md`. Commands and expected statuses: `docs/compatibility/production-runs.md`, Historical addon versions.

## Version-sensitive implementations

- `CraftingCpuLifecycle` recognizes exact optional CPU class names and lifecycle fields. Neo ECO through 21.2.0-beta3 uses `api.me.ECOCraftingCPU`; beta4 introduces `crafting.execution.ECOCraftingCPU` and worker lifecycle classes. Old cancellation leaves two responsibility units. Beta4 passes 41/41 excluding the fixture-only planner-ownership method; stable 21.2.0/21.2.9/21.2.10 pass 42/42.
- Lightning Tech 2.0.9 has the analogous old-CPU cancellation debt. The TimeWheel generation first tested in 2.1.0-beta.1 passes 9/9; stable 2.1.1 and 2.1.2-beta4 pass 35/35. Thunderbolt dependency ranges differ by generation. The first beta declares Data Energistics incompatible; do not generalize that conflict to stable 2.1.1.
- ExpandedAE 2.1.1 with contemporary ExtendedAE 2.2.32 boots without Federation, then fails Federation's target-binding Mixin because it overwrites `PatternProviderLogic.pushPattern`. Version 2.1.2 introduces the reflected five-argument target cache returning AE2's target type; 2.1.2/2.1.3/2.1.4 pass smart-blocking selection. Supply AdvancedAE, ExtendedAE and full AE2WTLib despite optional metadata: these releases access their classes unguarded.
- ExtendedAE-Plus smart doubling starts at 1.5.0. Versions 1.4.2/1.4.3/1.4.4 lack `SMART_DOUBLING` but ordinary accelerated-CPU crafting works. This is a feature boundary, not a global coexistence floor.
- First qualified generations on the recorded AE2 tuples: AdvancedAE 1.1.13 (34/34), ExtendedAE 2.2.7 (10/10), MEGA Cells 4.9.0 (12/12). Adjacent failures are upstream and reproduced without Federation. AdvancedAE is non-monotonic: 1.3.0, 1.6.0 and 1.6.1 have dedicated-server client-class failures on the tested tuples.
- UselessMod 2.4.5.9/10/11 pass 9/9. Furnace timeouts in 2.4.5.12 and 2.4.6 also occur with its real alloy furnace on one joined native AE2 grid. This control retains Federation and isolates projected cross-grid execution, not every Federation Mixin or historical fixture assumption; it does not prove an upstream-only defect or a global addon upper bound.
- Missing later blocks, cell encoders or auto-planner switches in historical Prototype, Pattern Disk, OmniSequence and Enhancements fixtures do not prove global production floors. Public-AE2-interface integrations do not acquire addon-specific compile-time floors just because a dedicated acceptance fixture exists.

## Investigation traps

- `compat_run.failure_hint` returns the first recognized error, not terminal server state. The early `No key layers` message is not evidence that startup hung. Inspect the final console lines and GameTest batch markers.
- The production test runner can fail every active unfinished test after one runtime exception, then stall later batches without a final report. Isolate the missing fixture instead of attributing every sibling failure to the addon.
- ECO beta4 full-run timeouts occur after startup at the fixture-only `ECOPlanningResultRegistry.isECOOwnedPlan(ICraftingPlan)` call. OmniSequence 1.3.0 reaches the tests before its old content lacks the fixture's `MatterFabricationStructure` class. Neither is a demonstrated production startup failure.
- Modrinth histories are incomplete relative to CurseForge. Verify old Glodium 2.0 from its actual CurseForge file; modern 2.2 is not a minimum-dependency control. Hash retrieved bytes rather than treating locally computed SHA512 as a publisher signature.
- The correct UselessMod release source is SorrowMist's GitHub project; the Modrinth `useless-mod` slug points at a different project.
- The two Xvfb UI runs independently report Jade 15.1.6 + JECharacters 4.5.14 and Jade 15.10.6 + JECharacters 4.5.30. Both pass 34 checks including actual Chinese pinyin search. Their development runtime uses AE2 19.2.17 / LDLib2 2.2.34, not the packaged-server AE2 19.2.18 tuple. Jade HUD contents were not individually visually qualified.

## Dependency-list scope clarification (2026-10-26)

- The user wants dependency lists limited to actual production integrations, not every addon covered by compatibility tests. MEGA Cells references occur in `common/src/compattest`, not production Java; its 4.9.0 qualification belongs in the compatibility matrix, not an optional runtime dependency declaration.
- Version-sensitive production adapters exist for Neo ECO, AdvancedAE, ExpandedAE and Lightning Tech; Jade and JECharacters have explicit client API integrations. A tested support starting point is still not automatically a proven strict API minimum.
- ExtendedAE-Plus and AE All Pattern motivate generic pattern-object refresh/global-provider reindexing, without a dependency on their specific APIs. Describe that behavior support separately from versioned optional dependencies. Conditional guide examples or a mod-presence check alone also do not establish an addon version requirement.
- User-confirmed rule: declare an optional addon version requirement only when Federation's production integration is genuinely version-sensitive. Dedicated handling, test coverage, or the introduction of an optional upstream feature alone is insufficient. ExtendedAE-Plus versions without Smart Doubling remain compatible through their existing functionality; 1.5.0 is a feature-introduction version, not a Federation compatibility floor. Do not promote a first tested passing version into a hard minimum without evidence that older versions violate the production integration contract.
- Jade/JECharacters clarification: `FederationJadePlugin` directly implements Jade APIs and registers both common server-data providers and client tooltip components. Jade integration can be ABI-sensitive, but 15.1.6 is only a tested version, not a proven strict minimum. `JechPinyin.find` reflectively looks up `Match.contains(String, CharSequence)`; absent mods, missing APIs or linkage failures return no matcher, and `SearchText` retains ordinary case-insensitive substring search. JECharacters 4.5.14 is likewise a tested endpoint, not a demonstrated hard dependency floor. Do not label both integrations as client-only hard version requirements.

## Four-adapter API minimum re-audit (2026-10-26)

- Inspected 44 SHA512-verified archived upstream JARs: 24 AdvancedAE, 10 Neo ECO, five ExpandedAE and five Lightning Tech. `javap -p -s` produced 202 present class declarations out of 245 checks; ExpandedAE overwrite annotations were additionally inspected with `javap -v -p`. Raw evidence and executed argument arrays are in ignored `neoforge-1.21.1/build/addon-version-boundaries/api-audit-2026-10-26.json`.
- All four have real production implementation/API coupling, but that does not validate the four previously suggested scalar minimums. `CraftingCpuLifecycle` uses exact CPU/host names, methods and private fields; `NeoEcoBatching` reflects batch contracts; ExpandedAE uses a specific target-cache constructor and target return type.
- Neo ECO: beta3 has the old `api.me.ECOCraftingCPU`; beta4 adds the recognized `crafting.execution.ECOCraftingCPU` and `ECOCraftingJobLifecycle.isTerminated(Level, UUID)`. The independent-CPU adapter boundary is 21.2.0-beta4; 21.2.0 is a stable-support choice, not the earliest compatible API. Earlier existing CPUs leave cancellation responsibility, unlike an absent optional new feature.
- AdvancedAE: withdraw 1.1.13 as a Federation API minimum. Version 0.6.0 already exposes `getSrc`, public `craftingLogic`, logic `getLastLink/getWaitingFor`, host `getPreviousState` and cluster `activeCpus/isDestroyed/getBlockEntities`; 1.1.12 has these as well. Its startup failure without Federation establishes an upstream tuple issue, not this API boundary. Do not substitute 0.6.0 as a proven strict minimum merely because it was inspected.
- ExpandedAE: 2.0.0 and 2.1.1 have a four-argument cache, addon-owned target return and `@Overwrite pushPattern`. Versions 2.1.2/2.1.3/2.1.4 have the consumed five-argument constructor, AE2 target return and no such overwrite. Together with the matched bare-versus-Federation runtime control, 2.1.2 is a directly evidenced adapter/Mixin boundary for the default integration.
- Lightning Tech: the consumed `TimeWheelCraftingCPU.getHost/getCraftingLogic`, logic `getLastLink/getWaitingFor`, host `isCpuActive/getTimeWheelCraftingCpuPool` and pool `hasPersistentState` already exist in 2.1.0-beta.1. Version 2.1.1 is the stable-support choice, not the first compatible API generation. Old 1.0.0 providers work without the recognized CPU/host classes, so do not label every earlier release globally incompatible; 2.0.9 specifically has the unrecognized CPU generation and observed cancellation failure.
- Guarded reflection failure is not automatically harmless compatibility: `CraftingProjectionService.observeJobs` marks unrecognized busy CPUs unknown, and job retirement depends on native termination evidence. The observed old-CPU ledger failures are meaningful correctness failures. Conversely, missing newer optional content or an unneeded CPU class does not establish a whole-mod minimum.
- NeoForge metadata semantics: `type="optional"` permits an absent target but still validates the version when present; it is a whole-mod loading constraint, not a feature-scoped recommendation. Metadata cannot express "require this range only when using the independent CPU." Do not copy CPU-scoped README ranges into global metadata without considering working older provider-only releases. Official 1.21.1 reference: https://docs.neoforged.net/docs/1.21.1/gettingstarted/modfiles/#dependency-configurations .

## Startup/coexistence criterion clarification

- The user explicitly distinguishes "can load and run together" from full support for optional addon features. Under that criterion, do not use CPU-generation support boundaries as whole-mod startup minimums.
- Archived `neoeco-1.0.0` starts and passes five Federation baseline scenarios; four newer-structure fixtures fail to form, so this is not full Neo ECO feature qualification. Archived `lightning-1.0.0` starts and passes all eight selected scenarios, including overloaded providers.
- ExpandedAE remains different: matched 2.1.1 boots without Federation but fails with Federation's target-binding Mixin; 2.1.2 starts and passes the selection. For startup-only metadata, this is the evidenced version gate. Neo ECO beta4 and Lightning beta.1 bounds describe independent-CPU integration, not the earliest proven coexisting releases; 1.0.0 is an observed coexisting sample for both, not proof that untested earlier releases fail.
- The user chose to omit optional-addon version entries from README Requirements; retain only the four baseline requirements. This is a documentation choice, not evidence that every addon combination is crash-free: ExpandedAE 2.1.1 has a confirmed startup Mixin conflict. No production metadata change was requested.
